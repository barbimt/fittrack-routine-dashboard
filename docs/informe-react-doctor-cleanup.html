1. ¿Qué es React Doctor?

Es una herramienta que revisa el código React buscando problemas de seguridad, bugs, rendimiento, accesibilidad y mantenimiento. Parecido a pasar un “linter avanzado” o un análisis estático, pero centrado en hábitos típicos de React.

No sustituye tus tests: te avisa de patrones peligrosos o frágiles. Nosotros corregimos el código y, solo cuando un aviso era un falso positivo intencional (por ejemplo, el kit de componentes shadcn), lo documentamos en doctor.config.json.

2. Mapa rápido React ↔ Vue (para orientarte)

  • Componente React ≈ componente Vue (SFC o Options API).
  • useState ≈ ref / reactive (dato local que dispara re-render).
  • useReducer ≈ un pequeño store local con mutaciones claras (similar a Vuex/Pinia en miniatura, pero dentro del componente).
  • useEffect ≈ watch / onMounted / suscripciones. En React se abusa mucho de él; la regla de oro es: no copies props a state “por si acaso”.
  • key en listas ≈ el :key de Vue: identifica cada ítem. Si usas el índice del array, al reordenar Vue/React “mezclan” filas.
  • Server Actions / código *.server.ts ≈ lógica que solo corre en el servidor (no en el navegador). En Vue suele vivir en tu API/backend.

3. Seguridad: quién escribe el “dueño” de una rutina

El problema

En FitTrack, cada rutina pertenece a un usuario (user_id). Si la app envía ese campo desde el cliente, alguien podría intentar guardar datos “como si fuera otra persona”.

Antes

La función de guardar rutina recibía un userId por parámetro y lo insertaba en la base de datos. Aunque los callers “bien educados” pasaban el usuario correcto, la API permitía confiar en un valor externo.

Ahora

1) El usuario se obtiene de la sesión autenticada (auth.getUser().
2) El user_id en inserts lo pone Postgres con DEFAULT auth.uid().
3) El helper se llama insertActiveRoutineTree.server.ts (solo servidor).

Por qué

Defensa en profundidad: aunque alguien manipule el front, la base de datos y las políticas RLS siguen atando filas a auth.uid(). No confíes en el navegador para decidir “quién eres”.

Analogía Vue

Igual que no dejarías que el front Vue envíe ownerId libremente a tu API: el backend toma el id del token/sesión. Aquí el “backend” es Supabase + Server Actions.

4. Login y redirecciones seguras

El problema

Tras el login (OAuth), a veces la URL lleva un parámetro ?next=/alguna-ruta para volver a donde estabas. Si aceptas cualquier valor, un atacante puede redirigirte a un sitio malicioso o a una pantalla privilegiada no prevista.

Antes

Se comprobaba poco más que “empieza por /”. Eso no basta: existen trucos tipo //evil.com o rutas inventadas.

Ahora

Existe sanitizeAuthRedirectPath: solo permite rutas conocidas de la app (/, /editor, /upload…). Además, las respuestas llevan cabeceras anti-clickjacking (frame-ancestors / X-Frame-Options).

Por qué

Las URLs son entrada de usuario. Trátalas como datos no confiables: allowlist (lista blanca), nunca “casi cualquier path”.

Analogía Vue

Como validar route.query.redirect en Vue Router antes de hacer router.push: no redirijas a lo que venga en la query sin filtrar.

5. Estado y formularios (import + panel de guardar)

5.1 Formulario de importar Excel

Antes

Varios useState sueltos: fase, archivo, rutina, errores, warnings… Al cambiar de paso había que actualizar muchos setters a la vez (fácil dejar estados a medias).

Ahora

Un useReducer con acciones claras: parse_start, parse_ok, save_error, etc. Un evento = una transición completa.

Analogía Vue

Parecido a pasar de muchos ref independientes a una máquina de estados / Pinia con mutaciones nombradas. Menos “estados imposibles”.

5.2 Panel “Guardar entrenamiento”

Antes

Muchos booleanos (isSaving, isSessionSaved, …). Combinarlos explota: ¿puede estar “guardando” y “ya guardado” a la vez?

Ahora

Una unión discriminada: status: "saved" | "unsaved" + busy. TypeScript ayuda a no pasar props contradictorias.

Por qué

Modelar el UI como “modos” (como pantallas de un wizard) es más fácil de razonar y de testear que una sopa de flags.

5.3 Flags de “guardando…” con try/finally

Antes

Se ponía isSaving = true, se hacía el await, y en varios caminos se volvía a false. Si algo fallaba raro, el botón podía quedarse en “Saving…”.

Ahora

El apagado del flag va en finally: siempre se limpia, haya éxito o error.

Analogía Vue

El mismo patrón que en una action async de Pinia: loading = true en try y loading = false en finally.

6. Efectos, fechas y “hidratación” (SSR)

El problema

FitTrack usa Next.js: primero puede renderizar en el servidor y luego “hidratar” en el navegador. Si durante el render llamas a new Date() o toLocaleDateString(), el servidor y el cliente pueden no coincidir (zona horaria / locale) y React se queja.

Antes

La fecha de “hoy” se calculaba al renderizar el dashboard (o con un useEffect que chocaba con las reglas de lint de React 19).

Ahora

Hook useClientToday con useSyncExternalStore: en servidor muestra un placeholder; en el cliente, la fecha real. Ambos lados coinciden en el primer paint.

Por qué

El render debe ser lo más “puro” posible. Reloj, aleatorio y locale son fuentes típicas de desajuste servidor/cliente.

Analogía Vue

En Nuxt (SSR) pasa lo mismo: datos que solo existen en el browser se cargan en onMounted o con composables client-only. Aquí usamos la API recomendada de React para ese caso.

Borrador del editor (useDirtyState)

React Doctor avisa si “copias props a state”. En el editor sí necesitamos un borrador editable distinto de la foto guardada (baseline). Eso es intencional, como un formulario dirty en Vue. Lo dejamos, con comentario/configuración que explica el falso positivo.

7. Accesibilidad en la fila de series (SetRow)

Antes

Toda la fila era un div con onClick para marcar la serie. Un ratón funciona; un teclado o lector de pantalla, no tanto. Además, meter click en un contenedor que ya tiene checkbox/input es confuso.

Ahora

Solo el checkbox marca la serie (control nativo accesible). La fila ya no es un “botón falso”.

Analogía Vue

Misma regla: evita @click en un <div> si puedes usar <button> o un input real. La semántica HTML ayuda a Vue y a React por igual.

8. Listas y keys estables

Antes

Algunas listas usaban key={index} (la posición). Si añades/quitas/reordenas series, React puede reutilizar el componente equivocado y “mover” el texto tipado a otra fila.

Ahora

Cada fila de series del editor tiene un id estable (crypto.randomUUID()). Las keys ya no dependen del índice.

Analogía Vue

Exactamente el mismo consejo del docs de Vue: :key="item.id", no :key="i", cuando la lista muta.

9. Limpieza, rendimiento “suave” y configuración

  • Dependencias sin uso eliminadas (sonner, date-fns, next-themes, etc.) → menos superficie de ataque y installs más limpios.
  • Constantes/helpers sacados fuera del componente (como funciones puras en un utils.js de Vue) para no recrearlos en cada render.
  • Context values memorizados en algunos componentes UI (evita re-renders en cadena; en Vue el reactivity lo disimula más).
  • pnpm-workspace.yaml con minimumReleaseAge y trustPolicy: espera unos días antes de instalar paquetes novísimos (higiene de supply-chain).
  • doctor.config.json: ignora ruido conocido (inventario shadcn en components/ui, artefactos .next), no para “esconder bugs reales”.

Migración DB importante: aplica supabase/migrations/20260811160000_user_id_default_auth_uid.sql (en local suele bastar pnpm supabase:reset).

10. Resumen para recordar (desde Vue)

  1. No confíes en el front para la identidad — el servidor/DB decide el user_id.
  2. Valida redirects como validarías query params en Vue Router.
  3. Estado relacionado → un solo modelo (useReducer / uniones de modos, no 8 booleanos).
  4. SSR = cuidado con Date/locale (como en Nuxt).
  5. HTML semántico > divs clickables.
  6. Keys estables = el mismo mantra que en v-for.
  7. Loading flags en finally siempre.

Resultado práctico: misma app FitTrack, pero más segura, más predecible y más fácil de mantener — con una puntuación React Doctor de 100/100 en esta rama.
